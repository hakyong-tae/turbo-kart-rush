# Drift Kart 2차 수정: 실제 기기에서 살아남기

2026-11-22. 소유자 지시: "최대한 크레이지게임즈에서도 살아남을 수 있게 해줘."
기준은 게임 저장소 `main` = `2fb46e4`. 1차 명세는 `docs/superpowers/specs/2026-11-20-drift-kart-crazygames-relaunch.md`.
이 파일은 다른 세션이 쓴 사본이다. 저장소 `docs/superpowers/specs/`로 옮겨 커밋한다.
측정 스크립트는 이 폴더의 `r2-audit/`에 있다(아래 4절).

## 1. 왜 또 하는가

1차 수정은 빠른 개발 기기(M1 Max)에서만 확인했다. CrazyGames 이용자는 학교 크롬북과 보급형 폰이 많고,
문서도 "4GB RAM 기기에서 매끄럽지 않으면 Chromium OS에서 비활성화"라고 적는다. 느린 기기 조건으로
다시 재 보니 1차 수정의 핵심이 발동하지 않는다.

CrazyGames 문서에서 다시 확인한 것(docs.crazygames.com, 26-11-22):

- 11/23 이후 시작하는 Basic Launch는 4개 지표로 잰다: 평균 플레이타임, D1 리텐션, 1분 이상 플레이 비율, 커버 클릭률.
- 기간은 최소 7일 + 500플레이(못 채우면 21일에 종료). **Basic Launch 중 게임·그림 업데이트는 심사 없이 바로 반영된다.**
- Basic Launch에 SDK는 필수가 아니다. 넣으면 초기 다운로드 크기를 첫 gameplayStart까지로 잰다.
- 물리는 144Hz·165Hz에서도 같아야 한다(이미 120Hz 고정 스텝). 게임 안 전체화면 버튼 금지(없음).
- 효과 없는 보상형 광고 버튼이 있으면 반려(이미 숨김). 영어 필수(있음).
- 모바일 조작 표시를 터치 감지에 의존하지 말고 SDK 시스템 정보를 쓰라고 한다.
- 글자는 907×510, 821×462(데스크톱 iframe), 800×450(모바일), DPR 1에서 읽혀야 한다.

## 2.0 정정 (같은 날 추가)

아래 2.1~2.3의 수치는 `main`이 아니라 **작업 중이던 `graphics-overhaul` 작업 폴더**(커밋 `7021d42` + 미커밋 변경)에서
잰 것이다. 재는 동안 게임 폴더가 그 브랜치로 바뀌어 있었다. `main`(`2fb46e4`)을 따로 내보내 빌드해 다시 잰 값:

| 조건 | `main` 2fb46e4 | `graphics-overhaul` 작업 폴더 |
|---|---|---|
| 1배: load 이전 초기화 긴 작업 | 1.4초 | 2.3초 |
| 4배: 첫 레이스 진입 | 진입(긴 작업 2.9초, 3초 제한에 0.1초 여유) | **로비** |
| 6배: 첫 레이스 진입 | **로비**(긴 작업 4.2초) | **로비** |
| 6배 medium 평균 fps (두 구간) | 48 / 74 | 39 / 44 |
| 6배 low 평균 fps (두 구간) | 51 / 73 | 29 / 48 |

결론은 그대로다: 3초 제한 문제는 `main`에도 있고(6배에서 실패, 4배는 아슬아슬), 단계를 낮춰도 fps가 같다.
달라진 점: 그래픽 개편이 초기화 비용을 약 0.9초(1배 기준), 프레임당 CPU 비용을 20~40% 늘렸다.
그래픽 개편과 이 문서의 P0·P1은 같은 파일(`gfx/quality.ts`, `ResolutionGovernor`, `PostFX`, `Game.ts`)을 만진다.
**이 문서의 작업은 그래픽 개편 위에서 한다**(`main`에서 따로 가지를 치지 않는다). 그래픽 개편은 low 단계의
프레임당 CPU 비용이 `main`보다 늘지 않아야 한다(위 표의 6배 low 수치가 기준).

## 2. 측정한 사실 (처음 잰 값: `graphics-overhaul` 작업 폴더, `npm run build:crazygames` 결과물, 새 저장 상태)

### 2.1 첫 접속 즉시 레이스가 느린 기기에서 발동하지 않는다 (가장 큼)

`Game.armFirstRace()`는 계정 기록을 3초 기다리고, 안 오면 로비를 연다. 그런데 이 3초가 게임 초기화의
메인 스레드 작업과 같이 흐른다. 초기화가 3초를 넘기면 긴 작업이 끝나자마자 타이머가 먼저 실행돼 로비가 뜬다.

| CPU 감속 | load 이벤트 | 결과 |
|---|---|---|
| 1배 | 2.3~3.0초 | 첫 레이스 진입 |
| 4배 | 4.2~5.7초 | **로비 + 출석 창** (긴 작업 1.8초+3.8초) |
| 6배 | 7.1~8.3초 | **로비 + 출석 창** |
| 4배, 터치 800×450 | 5.7초 | **로비 + 출석 창** |

M1 Max에서 4배 감속이면 보급형 노트북 수준이다. 크롬북·폰은 그보다 느리다. 즉 실제 이용자 대부분은
1차 수정 전과 같은 화면(로비 + 출석 창)을 본다. Verse8판도 같은 코드다.

### 2.2 시작하자마자 2.3초짜리 긴 작업 (M1 Max 기준)

개발 서버 프로파일(`r2-audit/prof.mjs`), 시작 구간:

- `ui/kartThumbnails.ts` `renderAll`: **1,939ms**. 캐릭터 선택 화면용 카트 16대 썸네일을 부팅 직후 그린다.
  첫 접속 이용자는 이 화면을 보지도 않는다. 대부분 셰이더 컴파일 대기다.
- `getShaderInfoLog` 1,223ms + `getProgramInfoLog` 278ms: three.js가 셰이더 오류를 동기 검사한다
  (`renderer.debug.checkShaderErrors` 기본값 true).
- `track/tracks/validate.ts` `validateAllTracks` 72ms, `trackThumbnails` 86ms 등 자잘한 것.
- `index.html`의 `<body>`에는 `<div id="app">`뿐이다. 번들(1.28MB)이 평가될 때까지 빈 화면이다.

### 2.3 레이스 프레임 비용은 CPU 쪽 렌더 순회다

`r2-audit/profrace.mjs`: 120fps에서 프레임당 약 2.6ms(M1 Max). 그중 렌더(`PostFX.render` → three.js 순회·
드로콜)가 73%, 후방 거울(`RearView.render`) 7%, 물리 6%, 오디오 5%.

| CPU 6배 감속, 1366×768 | 평균 fps | p95 프레임 |
|---|---|---|
| high | 37~44 | 34~42ms |
| medium | 39~44 | 34~50ms |
| low | 29~48 | 42~67ms |

그래픽 단계를 낮춰도 fps가 그대로다. 단계가 GPU 비용만 줄이기 때문이다.
그리고 `detectTier()`는 데스크톱에서 GPU 이름이 잡히면 코어·메모리를 보지 않는다. 인텔 내장 그래픽
크롬북(2코어, 4GB)은 `medium`을 받는다.

### 2.4 작은 화면

907×510, 821×462에서 배치는 깨지지 않는다. 결과 화면도 스크롤 없이 들어온다(`r2-audit/821x462-pc-06-results-b.png`).
11px 미만 글자: 결과 화면 `.unlock-label` 8px, 출석 `.attendance-gift` 9px, `.attendance-day`·`.profile-xp-n`·
`.logo-sub`·`.chip`·`.track-theme-chip`·`.track-lock-text` 10px, 차고 탭 10.5px.

### 2.5 결과 화면

"다음 레이스" 버튼은 있지만 누르지 않으면 그대로 멈춰 있다. 평균 세션이 두 판이었다.

## 3. 바꿀 것 (우선순위 순)

### P0-1. 첫 접속 판정을 기기 속도와 무관하게

- CrazyGames판(`PLATFORM.hosted === false`)은 기록이 이 브라우저에 있다. 타이머 없이 판정한다:
  기록을 읽는 즉시(동기든 첫 마이크로태스크든) 결정하고, 로비를 한 프레임도 보여 주지 않는다.
- Verse8판은 제한 시간을 유지하되, 초기화의 긴 작업이 끝난 뒤(첫 프레임이 그려진 뒤)부터 센다.
  메인 스레드가 막혀 있던 시간은 세지 않는다.
- 검사: CPU 6배 감속 + 새 저장에서 `title` 상태가 화면에 보이지 않고 `countdown`에 도달한다(PC, 터치 둘 다).

### P0-2. 시작 비용 줄이기

- 카트 썸네일은 필요할 때 그린다: 캐릭터 선택·일일 도전·기록·결과 화면이 실제로 그림을 요청할 때,
  또는 로비에서 한가할 때 한 프레임에 한 대씩. 레이스 로딩·카운트다운·레이스 중에는 그리지 않는다.
  결과 화면의 `getLookThumbnail`은 그 한 장만 그린다.
- 프로덕션 빌드에서 `renderer.debug.checkShaderErrors = false`(개발 서버에서는 유지). 썸네일용·차고용
  렌더러도 같다.
- `validateAllTracks`는 개발 서버·테스트에서만 돈다.
- `index.html`에 JS 없이 바로 그려지는 시작 화면을 넣는다: 어두운 배경, 워드마크(빌드 타깃별 이름),
  움직이는 진행 표시. 인라인 CSS만 쓰고 외부 요청은 없다. 게임 UI가 준비되면 사라진다.
  로딩 화면과 색·서체가 이어지게 한다.
- 목표(측정값을 문서에 적는다): CPU 6배 감속에서 첫 그리드까지 시간을 지금보다 40% 이상 줄인다.
  1배에서 load 이전 긴 작업 합계 1초 미만.

### P1-1. 느린 기기는 low로

- `detectTier()`: 데스크톱에서 GPU 이름이 `medium`(내장 그래픽)이어도 `hardwareConcurrency <= 4`이고
  `deviceMemory <= 4`이면 `low`. UA에 `CrOS`가 있고 내장·모바일 GPU면 `low`.
  테스트(`quality.test.ts`가 있으면 거기)에 사례를 추가한다.
- 해상도 거버너가 최저 배율에서도 프레임이 길면(CPU 한계) 다음 레이스부터 한 단계 낮춘다.
  설정에서 고른 단계는 건드리지 않는다.

### P1-2. low 단계가 CPU 비용도 줄이게

먼저 잰다: 프레임당 드로콜·삼각형 수(`renderer.info`, `autoReset` 끄고 한 프레임 합계), 그림자 패스 비중.
그 다음 low에서(필요하면 medium 일부도):

- 후방 거울 패스를 끈다(위협 표시는 기존 글자·화살표 경고로).
- 그림자: 끄거나, 움직이지 않는 것은 한 번만 굽고 카트만 블롭 그림자.
- 움직이지 않는 장식(관중석, 나무, 타이어 벽, 표지판)은 `matrixAutoUpdate = false`,
  같은 재질끼리 병합하거나 인스턴싱. 이미 병합돼 있으면 건너뛴다.
- 환경 프로브 갱신 주기, 파티클 수 등 프레임마다 도는 것 중 큰 것.
- 목표: `r2-audit/perf.mjs` 기준 CPU 6배 감속·low에서 평균 50fps 이상, p95 33ms 이하
  (지금 29~48fps). 화면이 눈에 띄게 초라해지면 목표보다 화면을 우선하고 수치를 적는다.

### P2-1. 결과 화면 자동 진행

- 보상 연출이 끝나면 주 버튼("다음 레이스")이 8초에 걸쳐 차오르고, 다 차면 다음 레이스를 시작한다.
  버튼 문구 옆에 남은 초를 보여 준다.
- 멈추는 조건: 결과 화면에서 다른 버튼·패널을 누르거나 키보드로 포커스를 옮김, 탭이 가려짐,
  창 포커스를 잃음. 멈추면 다시 시작하지 않는다.
- 하지 않는 경우: 컵의 마지막 경기 결과, 온라인 레이스, 일일 도전, 리타이어한 판,
  "내일 보상" 카드나 레벨업·새로 열림 연출이 아직 끝나지 않았을 때.
- 설정에 "다음 레이스 자동 시작" 끄기 항목(기본 켬).
- 두 판 연속으로 아무 입력 없이(조향·가속 입력 0) 끝났으면 자동 진행을 멈춘다. 자리를 비운 사람을
  계속 레이스에 넣지 않는다.

### P2-2. 작은 글자

2.4의 항목을 821×462, DPR 1에서 11px 이상으로. 줄바꿈·잘림이 생기면 배치를 고친다.
`.unlock-label`(8px)이 가장 급하다.

### P3. CrazyGames SDK (CrazyGames판만)

문서: docs.crazygames.com/sdk/intro, /sdk/game, /sdk/data, /sdk/user, /requirements/technical. HTML5 v3 SDK.
먼저 문서를 읽고, 문서와 아래가 다르면 문서를 따르고 차이를 적는다.

- `src/platform/crazygames.ts` 한 곳에 감싼다. 다른 코드는 SDK를 직접 부르지 않는다.
  SDK가 안 뜨거나(로컬, 차단) 초기화가 실패하면 전부 아무 일도 하지 않고 게임은 그대로 돈다.
  SDK 로딩이 첫 레이스를 기다리게 하지 않는다(제한 시간을 두고 넘어간다).
- 이벤트: 로딩 시작·끝, `gameplayStart`(레이스 시작·일시정지 해제·다음 레이스), `gameplayStop`
  (결과 화면·일시정지·로비). 포커스를 잃었다고 `gameplayStop`을 부르지 않는다(문서 규칙).
  `happytime`은 1등과 컵 우승에만.
- 저장: 계정 기록(`tkr.local.user`)을 SDK 데이터 모듈에도 쓴다. 시작할 때 SDK 쪽과 로컬 중
  진행이 더 많은 쪽(레이스 수 → 코인 순)을 쓴다. 덮어써서 진행을 잃는 일이 없어야 한다. 1MB 한도.
- 설정: `muteAudio`를 따른다(게임 안 소리 설정보다 우선).
- 기기: SDK 시스템 정보의 기기 종류로 터치 조작 표시를 정한다. SDK가 없으면 지금 방식.
  언어: SDK 로캘이 `ko`면 한국어, 아니면 영어. 이용자가 고른 언어가 있으면 그쪽.
- 광고 호출은 넣지 않는다(Basic Launch에서 광고는 꺼져 있다).
- `tools/crazygames-check.mjs`의 "외부 요청 없음" 검사는 SDK 주소 하나만 허용하도록 고친다.
- SDK를 뺀 빌드도 만들 수 있게 한다(환경 변수 하나). QA에서 SDK가 문제 되면 빼고 낸다.

## 4. 측정 도구 (`r2-audit/`, 이 폴더)

- `boot.mjs <base> <rate>`: 첫 접속 판정 시각과 긴 작업.
- `perf.mjs <base> <rate> <gfx|auto> [pc|touch]`: 첫 레이스 진입 여부, 그리드까지 시간, 레이스 fps.
- `prof.mjs <base>`: 시작 구간 CPU 프로파일(개발 서버). `profrace.mjs <base>`: 레이스 구간.
- `sizes.mjs <base> <out> <w> <h> <pc|touch>`: 작은 화면에서 첫 세션을 걸으며 11px 미만 글자와 잘림을 적는다.

`<base>`는 프로덕션 빌드(`vite preview --mode crazygames --outDir dist-crazygames`) 또는 개발 서버.
CPU 감속은 CDP `Emulation.setCPUThrottlingRate`다. GPU는 느려지지 않으므로 GPU 한계는 이 도구로 못 잰다.
쓸 만한 것은 저장소 `tools/lowend-check.mjs`로 옮겨 검사로 남긴다(6배 감속에서 첫 레이스 진입, 그리드까지 시간, fps).

## 5. 하지 않는 것

- 해금 사다리·보상 수치 변경, 새 모드, 그림 스타일 변경.
- push, Verse8 배포, CrazyGames 포털 제출. 전부 로컬에서 끝낸다.
- `package-lock.json`의 기존 변경은 건드리지 않는다. `verse8` 원격 주소의 토큰은 출력하지 않는다.
- 커버·미리보기 영상은 다른 세션이 다시 만든다.

## 6. 진행 방식과 검증

- `main`에서 새 브랜치 `crazygames-r2`. 항목별로 커밋한다. P0 → P1 → P2 → P3 순서로, 앞 단계가

### 7.1 명세와 다르게 한 것

- **P0-1, CrazyGames판도 타이머를 남겼다.** 명세는 "타이머 없이 동기 판정"이다. 기록은 브라우저에 있지만 읽는 코드
  (`verse8/localServer.ts` → `server.js`)가 동적 import라 한 번은 비동기다. 그래서 두 판 모두 같은 방식으로 고쳤다:
  대기 시간을 **실제로 그린 프레임**으로 센다(프레임 하나가 아무리 길어도 0.1초까지만 더한다). 메인 스레드가 막혀
  있던 시간은 세지 않으므로 초기화가 몇 초 걸려도 기록이 먼저 읽힌다. 한도는 Verse8 호스트 안 3초, 그 밖(기록이
  브라우저에 있는 경우) 10초. 로비는 한 프레임도 보이지 않는다(`first-boot` 클래스가 붙어 있는 동안 숨김,
  `lowend-check`의 `lobbyShown`으로 검사).
- **P0-2, `validateAllTracks`는 이미 개발 서버에서만 돌았다**(`import.meta.env.DEV`). 고칠 것이 없었다.
  프로파일에 잡힌 것은 개발 서버라서다.
- **P0-2, 썸네일용 렌더러를 하나로 합쳤다.** 명세는 "필요할 때 그린다"까지다. 그리는 시점만 미루면 캐릭터 선택을
  여는 순간 같은 2초가 온다. 그래서 한 프레임에 한 대씩 `compileAsync`로 그리고, 시트와 결과 화면·기록의 룩
  썸네일이 렌더러 하나를 같이 쓴다(전에는 룩 한 장마다 WebGL 컨텍스트를 새로 만들고 셰이더를 다시 컴파일했다).
- **P0-2에 더한 것**(명세에 없음, 6배 감속의 그리드 시간을 줄이려고): 환경 프로브를 첫 레이스 로딩 때 만든다,
  품질 판정이 두 번째 WebGL 컨텍스트를 열지 않는다, 카트의 둥근 상자 부품을 8대가 공유한다, 지면·도로 얼룩
  노이즈를 1/4 크기로 계산해 늘린다, low 단계는 지형 메시와 노이즈 타일이 작다.

  밑동 그늘(`foliage.ts`의 blob)로 대신한다. 둘 다 그래픽 개편에서 이미 넣은 것이다.
- **P1-2, 후방 거울은 끄되 경고는 남겼다.** 명세는 "위협 표시는 기존 글자·화살표 경고로"인데, 뒤에서 오는 등껍질을

## 8. 엔진 배기음 교체 (2026-11-22, 명세 밖 추가 지시)

소유자 지시: soundeffectgenerator.org의 "rider kart" 효과음을 쓴다(상업용 라이선스는 소유자가 확인), 기존 배기음이
"너무 하이하고 찢어지는 소리"라는 피드백이 많았다. 출처·라이선스·가공 내용은 `src/assets/audio/CREDITS.md`.

### 8.1 무엇이 찢어졌나

기본음은 `scream` 하나가 아니라 체급별로 달랐다(`CLASS_PACK`): 경량 = `electric`, 중량 = `scream`, 헤비 = `rumble`.
**처음 타는 카트(Zippy Nova)가 경량**이라, 새 이용자가 듣던 소리는 인버터 고음이었다. 리미터에서 기본 주파수가 2.1kHz,
에너지의 99%가 2kHz 이상이다(아래 표). `scream`은 750Hz·21%였다.

### 8.2 바꾼 것

- **기본음**(엔진 팩을 사지 않은 카트, 세 체급 모두): 녹음된 배기 루프가 몸통. 회전수에 따라 0.8~2.0배로 재생하고
  (기어 변속의 낙차는 그대로: 재생 속도가 같은 회전수 값을 따른다), 저역 통과 2.0~4.6kHz로 금속성 틱을 걸러 내고,
  600~1,150Hz를 11dB 올린다. 녹음은 에너지의 80%가 250Hz 아래라 폰 스피커에서는 거의 안 들리기 때문이다.
  신스는 30%로 내려 저역 보강만 한다(기본 주파수 53~178Hz, 옥타브 레이어·포먼트·클립 모두 약하게).
  체급 차이는 전체 음높이로: 경량 +15%, 헤비 −14%.
- **받기 전·실패 시**: 같은 신스가 100%로 난다(낮게 조율된 소리). 파일(21KB)은 첫 화면이 그려진 뒤 받기 시작하고
  (측정: 1.1~1.2초 시점), 오디오 컨텍스트가 생기면 디코딩한다. 아무것도 이 파일을 기다리지 않는다.
- **8대 모두 루프를 쓴다.** 루프 한 개 재생은 오실레이터 묶음보다 싸다. 카트마다 루프의 다른 지점에서 시작한다.
- **`?engine=old`**: 기본음을 전처럼(체급별 `electric`·`scream`·`rumble`) 낸다. 두 판 공통. 출시 전에 뺄지는 소유자가 정한다.
- **유료 팩**: `rumble`·`diesel`·`chiptune`은 그대로. `electric`과 `turbine`은 같은 문제가 있어 낮췄다(성격은 유지):
  `electric` 최고음 1.8kHz → 1.1kHz, 3배음·포먼트 약하게(4kHz 이상 20.5% → 1.6%). `turbine` 1.5kHz → 1.1kHz,
  저역 통과 14kHz → 8kHz(2kHz 이상 37.6% → 32.7%, 4kHz 이상 14.3% → 9.4%). 터빈은 휘슬이 성격이라 더 내리지 않았다.
- 차고에서 무료 엔진 이름이 "Scream V10 / 스크림 V10"이었는데 더는 그 소리가 아니라 "Stock / 기본 엔진"으로 바꿨다.

음량은 기존 중량 기본음에 맞췄다(±0.3dB). 다만 루프는 펄스라 피크가 높다(0.42~0.72, 기존 0.17~0.31).
마스터에 컴프레서·리미터가 있어 잘리지는 않지만, 여러 대가 겹칠 때의 체감 음량은 들어 봐야 안다.

### 8.4 확인한 것과 못 한 것

- 실제 레이스(CrazyGames판 빌드)에서 루프가 1.2초에 같은 오리진에서 요청되고 8대 모두 루프로 넘어간 것,

  (빌드 1.59MB·12파일, mp3 포함). 테스트 324개, `ui-smoke` 4/4, 6배 감속 첫 접속 그대로 진입.

  8대가 겹친 소리, 음악과의 균형은 사람이 들어야 한다. `node tools/engine-spectrum.mjs --wav <폴더>`로 위 표의
